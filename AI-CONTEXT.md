# Project Context & Operating Protocol \n\n## 1. Project Overview\n**Purpose:** The application is a digital signature service called **Helppo Allekirjoitus** ("Easy Signature"). It allows users to upload PDF documents, add recipients (signers), process a per-signature payment instead of a subscription, and securely authenticate via Finnish Trust Network (eIDAS & FTN compliance).\n**Target Audience:** Consumers and businesses in Finland who need legally binding digital signatures without recurring monthly fees or account registration.\n**Core Promise:** A secure, "zero-knowledge" flow where files are destroyed within 24 hours of process completion.\n\n## 2. Tech Stack & Infrastructure\n* **Frontend Framework:** React 19 (managed with Vite) + TypeScript.\n* **Routing:** `react-router-dom` (v7).\n* **Styling:** Vanilla CSS (`index.css`) with CSS variables for a glassmorphic, modern design system. Minimal external CSS libraries.\n* **State Management:** Local React hooks (`useState`, `useEffect`) and native browser `sessionStorage` (crucial for managing data between authentication/payment redirects).\n* **Database & Backend:** Supabase (PostgreSQL). Employs Edge Functions for server-side operations (auth callbacks, email dispatches, Stripe webhooks, and cleanup jobs). \n* **API Integrations:**\n  * **Stripe:** For handling one-time payments natively via `@stripe/react-stripe-js`.\n  * **Idura / OIDC:** Custom integration handling the Finnish banking authentication flow.\n  * **Browser Crypto:** Uses `jose` and `jsonwebtoken` for secure cryptographic data handling.\n\n## 3. Architecture & Directory Structure\n* **High-Level Structure:**\n  * `/src/`: Contains all frontend React code. Top-level `*View.tsx` files (e.g., `UploadView.tsx`, `VerifyView.tsx`) represent the main route pages.\n  * `/src/hooks/`: Contains highly specialized custom hooks (like `useDocumentFlow.ts`) that orchestrate view state transitions.\n  * `/src/lib/`: External service clients like the Supabase setup (`supabase.ts`) and global error reporting (`errorReporter.ts`).\n  * `/supabase/functions/`: Serverless Edge Functions that handle external events, email sending, daily cleanups, and PDF packaging.\n* **Architectural Pattern:** The app utilizes a **"Thick Database / Thin Controller"** approach. The frontend directly invokes PostgreSQL RPC functions (`supabase.rpc(...)`) for data manipulations, heavily leaning on Row Level Security (RLS) and database logic rather than an intermediary Node.js backend layer.\n\n## 4. Data Flow & State Management (Crucial)\n* **Global State & Session Recovery:** Because the signature flow requires the user to leave the application multiple times (Stripe for payment, Bank login for authentication), local state is aggressively cached into `sessionStorage` (`appState_data`, `appState_view`). When a user is redirected back, `useDocumentFlow.ts` intercepts URL params (e.g., `redirect_status`) and restores the frontend context from storage.\n* **Document Workflow State Machine:** `useDocumentFlow.ts` acts as the brain. The view state transitions through predefined phases: `'loading' | 'start' | 'payment' | 'authenticating' | 'processing' | 'waiting' | 'success' | 'error'`.\n* **Data Fetching/Mutating:** Read and write actions are abstracted through Supabase RPCs (like `get_document_by_id`). \n* **Real-time Status Polling:** When waiting for additional signers (the `'waiting'` state), the application polls the database every 4 seconds to push the UI into completion locally when all signers are verified. \n* **Observer / Sponsor Flow:** Specific logic exists where the sender can act solely as an observer/payer (paying for an entire group without signing themselves).\n\n## 5. Coding Standards & Conventions\n* **TypeScript Pragmatism:** The codebase prefers interfaces and types (e.g., `SignatureData`), but allows inline typing and `any` loops (`.map((s: any) => ...)`) where strict API typings aren't rigidly enforced. It is a pragmatic, rapid-development typescript setup.\n* **Error Handling:** Try/catch blocks encompass external calls, feeding into both a user-facing toast library (`react-hot-toast`) and a centralized analytic catch (`reportError` from `lib/errorReporter.ts`).\n* **Component Composition:** Large, unified view components. `DocumentFlow.tsx` effectively operates as a master UI controller rendering `PaymentView`, `ProcessingView`, or `SuccessView` depending on the state machine, rather than separating them into diverse functional routes.\n* **Class Naming:** Follows a customized utility class pattern (e.g., `.form-input`, `.btn-primary`, `.glass-card`) relying entirely on `index.css` rather than Tailwind CSS utilities. \n* **Fail-safes:** Built-in "Auto-Recovery" states. If a document enters a state where signatures are received but the final PDF failed to generate due to server load, the hook forces the app back into the `'processing'` state automatically.
